## Design interview: authority boundary

The owner accepted **every active paired Device bearer** as a request authority, with no separate per-Device grant. The owner also accepted the existing remote enrollment chain: A may create B's pairing token, D may consume it, and D may then request B's unlock or sign-in. Pairing remains directed: A→B does not grant B→A authority; reverse access requires another pairing. The target-wide capability is enabled by default on B; a target-local OS administrator may explicitly disable it. Disabling rejects remote entry requests while retaining enrolled local credentials; re-enabling does not require per-account enrollment again, and credential deletion is separate. The switch governs both unlocking an existing session and signing in at a running OS greeter when local credentials are ready. These are accepted design decisions, not implemented policy; see the [authority decision](https://github.com/moeru-ai/auv/blob/85f638525c669e56aac3ce4792e39292563944c6/docs/ai/references/session-api/2026-09-27-device-unlock-authority-decision.md), [pairing terms](../../../TERMS_AND_CONCEPTS.md), and the [paired-bearer administration test](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-daemon/src/server_test.rs). Concrete login-session selector representation is deferred to the implementation contract slice.

Each OS account must be enrolled separately on B with a stored usable login credential. The owner confirmed that the default-on target-wide switch does not itself make every account eligible, even if Linux can unlock a particular existing session without credential entry. Lock-only enrollment without a stored credential is excluded. All active paired callers share authority only over target-locally enrolled accounts. A target-local OS administrator may enroll or delete enrollment for any account without that account holder's separate confirmation; a non-administrator may enroll or delete only their own OS account locally. Deletion makes subsequent remote requests for that account ineligible. Enrollment and deletion must derive the local caller's identity from the OS rather than an untrusted username argument.

The owner rejected implicit physical-console selection for `devices unlock`: each request must specify a user or an operating-system login session. A user selector resolves only when exactly one eligible login session matches; multiple matches are an ambiguity error requiring a specific session selector. While B's target-wide remote-entry capability is enabled, active paired Devices may obtain user, session identifier, and lock-state facts through a read-only Device operation; disabling that capability rejects session-list requests too. Provisional CLI spelling is `auv devices sessions --device-id B`. This is a target selector within a Device operation, not a revival of AUV's retired public `SessionService`; [AUV Session terminology](../../../TERMS_AND_CONCEPTS.md) currently reserves that word for internal resources. The exact query name and selector wire representation remain open.

The owner wants the same Device operation to sign in a selected user at a running OS greeter when no session exists, creating a new session. This broadens the intended behavior beyond the live proofs, which covered only already logged-in locked sessions. The result must distinguish `unlocked_existing_session` from `signed_in_new_session`; those names are provisional. The signed-out path is not yet implemented or validated on macOS, Linux, or Windows. FileVault/LUKS and other preboot states are out of scope: the ordinary Devices API requires a running OS and reachable target daemon. A future preboot path would need a separate out-of-band mechanism and owner-approved design.

If another user is actively using B's physical desktop, a remote request to sign in a selected user who has no session must fail with an occupied-desktop error. It must not switch users or interrupt the current desktop. If the other user's physical session is locked, the target may switch to the login UI and sign in the selected user, provided it preserves the other user's locked session. A platform that cannot preserve it must fail this request. This signed-out, multi-user path has not been live-probed.

The owner retained one public CLI action named `auv devices unlock` for both effects. Its structured result distinguishes an existing-session unlock from a new-session sign-in. Exact selector flags, request and response fields, and library method names are still provisional; this is a naming decision, not a claim that either API path exists yet.

If the selected user's desktop is already logged in and unlocked, the owner wants a successful `already_usable` no-op result (provisional variant name). That path must not resolve a stored OS credential, post input, or change focus. Thus the result has at least three semantic outcomes: already usable, unlocked existing session, and signed in a new session; delivery metadata alone does not stand in for any of them.

The owner accepted a kubelet-like host lifecycle: the target daemon starts with the OS under a service manager and remains reachable across graphical logout. Kubernetes documents kubelet as a node daemon managed by a service manager such as systemd, independent of interactive login ([kubeadm/kubelet integration](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/kubelet-integration/)). AUV currently exposes foreground `auv serve`; the reference terms describe service-manager integration as future work ([AUV daemon terms](../../../TERMS_AND_CONCEPTS.md)). A user-login LaunchAgent or app-owned child may disappear on logout. A machine-level listener and platform-specific access to the selected login UI are distinct responsibilities. See the [host lifecycle decision](https://github.com/moeru-ai/auv/blob/85f638525c669e56aac3ce4792e39292563944c6/docs/ai/references/session-api/2026-09-27-device-login-host-lifecycle-decision.md); neither part is implemented for signed-out login.

The owner accepted persistent enrollment of a usable OS login credential on the target, supplied locally and readable by the actual machine-level service identity before user login. A system-level protected keystore/keychain is preferred. If none is suitable, a local administrator may explicitly select a plaintext credential file; there is no automatic fallback and remote paired callers cannot make that choice. The enrollment flow must prove service-side retrieval before reporting readiness; the remote request still carries no credential. See the [credential decision](https://github.com/moeru-ai/auv/blob/85f638525c669e56aac3ce4792e39292563944c6/docs/ai/references/session-api/2026-09-27-device-entry-credential-decision.md). No live probe has established such persistent storage. The concrete protected backend, plaintext file access rules, and rotation behavior remain open.

If the OS clearly rejects an enrolled credential, the target suspends remote entry for that account until local re-enrollment. A later paired request must not retry the same stored secret. This rule does not infer credential rejection from mere input-delivery failure or an unverified screen state; platform-specific rejection evidence is still unproven.

## Define the effect before choosing an OS API

The accepted target behavior includes both **unlocking an existing, locked graphical user session** and **signing in at a running OS greeter when the selected user has no session**. A FileVault-protected Mac waiting for preboot volume unlock is a third, excluded state. A Device result must not collapse the first two states into one `success` boolean. Screen pixels are unnecessary for the caller, but the target still needs an independent observation that the intended session became usable; input submission or a daemon response alone is insufficient. These distinctions follow the platform session boundaries in the [driver research](../driver/2026-09-27-lock-and-login-screen-deep-research.md).

There are three materially different authorization models:

| Mode | What authorizes OS unlock | Consequence |
| --- | --- | --- |
| Per-request OS credential | The target OS validates a password or another supported sign-in factor provided for this request | The Devices API must carry a secret without placing it in CLI argv, generic invoke inputs, replay, tracing, error strings, or screenshots. Native authentication and platform validation remain necessary. |
| Locally enrolled unlock policy | An owner configures the target host to treat a particular remote request as authority to unlock | This is an explicit change to the target's lock security policy. It is platform-specific and cannot be inferred from AUV pairing. |
| Pairing credential alone | The ordinary AUV paired Device bearer replaces OS login validation | This is not the selected credential path. Pairing authorizes the *request*, while the target must still use its local OS unlock mechanism. [AUV terms](../../../TERMS_AND_CONCEPTS.md), [authenticator](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-api-server/src/authentication.rs). |

The target-local secret mode below is the accepted behavior, and the paired-bearer request authority and CLI action name are decided. Storage backend, exact selector and result shape, and first implementation platform remain open choices.

## Target-local secret flow

```text
A: auv --device B devices unlock
  -> authenticated request to B's persistent daemon
  -> B checks its locally configured unlock policy and session state
  -> B resolves a secret reference from its local store
  -> B's session-aware host submits credentials through the OS login path
  -> B independently observes whether the intended session unlocked
  -> A receives a typed result without the secret
```

There is no need to route the password back to A or invoke generic `input.typeText` remotely. The local host may reuse low-level driver key delivery once it has selected the correct OS session, but the unlock operation owns the secret lookup, target selection, and verification. A tracing policy must exclude the secret value and secret-bearing driver payloads from inputs, reports, replay records, errors, and artifacts; ordinary delivery metadata may still be recorded. An `env` file can be an explicit provisioning backend if B's host can read it, but it is plaintext-at-rest configuration and does not solve OS-session input or verification.

The target B must retain a local audit record for remote entry requests, including the authenticated paired Device ID, selected OS user or login session, request time, and typed outcome (including rejection and no-op). The record must never include the stored credential, secret-bearing key events, or login/password-field screenshots. B's local OS administrator may read all of this history; an ordinary local user may read entries concerning their own OS account; a paired remote caller receives only its current request result and may not browse audit history. The concrete store and retention policy remain open.

Current `RunService` lists and retrieves Runs belonging to the authenticated caller, including a paired bearer ([daemon Run ownership](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-daemon/src/daemon/mod.rs), [paired Run test](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-daemon/src/server_test.rs)). Thus storing unlock audit entries as ordinary Runs owned by the remote caller would expose that caller's past unlock history, contrary to the accepted boundary. Any integration with implicit Run recording must keep the target-local audit history out of remote Run read paths, while still excluding credential and input payloads. The exact Run ownership/storage integration is an implementation design question.

**Storage availability is platform-specific.** On macOS the data-protection keychain is available only in a user login context, not from a system LaunchDaemon; the system-context keychain search list contains the System keychain. A user-login keychain can also require unlocking or prompt for access. Thus a secret that the pre-login/locked host must read cannot be assumed available merely because it is in the user's default Keychain. [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains), [Apple Keychain Access](https://support.apple.com/en-lamr/guide/keychain-access/kyca1242/mac). Windows DPAPI supports user- and machine-bound protection with different access implications, so the exact service identity must be fixed before choosing a store. [Microsoft `CryptUnprotectData`](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata), [DPAPI scope](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dpapidataprotector.scope?view=netframework-4.8.1). Freedesktop Secret Service collections may lock and require an interactive prompt, so a user keyring is not automatically available during unattended unlock. [Secret Service locking](https://specifications.freedesktop.org/secret-service/latest/unlocking.html).

## Existing AUV path

This section records the pre-implementation baseline. Its repository code
links are pinned to PR #198 base `2957b9f`, before the candidate unlock APIs.

`DeviceService` currently offers only `ListDevices` and `GetDevice`; `auv devices` exposes inventory, pairing, trust administration, and profiles. Paired Device credentials authenticate remote daemon calls. The first-party local Driver Runner is a daemon-spawned child, so it inherits the daemon's session and cannot gain a login/secure-desktop context merely through a new RPC. A direct Device action could present as **provisional** `auv --device <name> devices unlock` and `Devices::unlock(...)`, routed to the selected target daemon. Its implementation owner must be a host-side session capability with a process that remains available while locked. [Device proto](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/proto/auv/api/daemon/v1/device.proto), [CLI](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-cli/src/commands/devices.rs), [Rust facade](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv/src/devices.rs), [Runner spawn](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-daemon/src/daemon/runner.rs).

This is a Device lifecycle action, not an app/window command. The daemon should authorize the request and route it to a platform capability. The typed result needs to distinguish request admission, native delivery/authentication, and observed unlock; an `InputActionResult` remains appropriate for actual synthetic input attempts, but it does not by itself prove the OS session unlocked. This proposed boundary uses AUV's existing [input result semantics](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-driver-common/src/input.rs) and [Run vocabulary](../../../TERMS_AND_CONCEPTS.md); it does not authorize adding new RPCs yet.

## Platform paths and limits

### Windows

Windows documents that unlocking a locked workstation requires sign-in information. A normal AUV user-process `SendInput` path cannot stand in for an OS-authenticated unlock. A target service/worker can reach the Winlogon desktop, as Sunshine and RustDesk demonstrate for remote control, but *seeing or typing at Winlogon* is different from a direct OS unlock primitive. `WTSConnectSessionW` accepts a password when connecting one Remote Desktop Services session to another; it is a session-connect API, not a documented generic `UnlockWorkstation` call. RDP can authenticate a remote session under its own policy, which is also not necessarily unlocking the physical console. [Windows unlock policy](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/interactive-logon-require-domain-controller-authentication-to-unlock-workstation), [WTSConnectSessionW](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsconnectsessionw), [AUV Windows input](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-driver-windows/src/input.rs), [secure desktop source review](../driver/2026-09-27-lock-and-login-screen-deep-research.md).

For a credential-based proof, the source-backed path is an installed privileged remote-control host in the target session delivering credential entry to Winlogon and observing a session transition. A headless API that authenticates and unlocks without that UI requires a separately verified Windows mechanism; `LogonUser` creating a token should not be assumed to change the console's lock state.

### macOS

Apple's Authorization Services authenticate access to defined rights; their public documentation does not expose a general `unlockScreen(password)` operation. A `LoginWindow` LaunchAgent can run in the graphical login context, but Apple does not promise that ordinary ScreenCaptureKit or Core Graphics event posting will unlock it. The installed Sky package contains a lock-screen guardian and Authorization Plugin associated with `system.login.screensaver`; this is local-package evidence for one product's active-session auto-unlock design, not a supported general AUV API recipe. Apple's plug-in guide depends partly on nonpublic authorization tags, and DTS has identified some unlock-rule modifications as unsupported. [Authorization Services](https://developer.apple.com/documentation/security/authorization-services), [Apple LoginWindow context](https://developer.apple.com/forums/thread/696859), [plug-in guide](https://developer.apple.com/documentation/security/extending-authorization-services-with-plug-ins), [DTS](https://developer.apple.com/forums/thread/824458), [Sky inspection](../driver/2026-09-27-sky-cua-lock-screen-research.md).

A macOS proof should first test an already logged-in locked session with a signed, authorized host and verify the resulting session state. FileVault preboot unlock remains separate; Apple documents an SSH FileVault unlock path on Apple silicon/macOS 26+ under specific conditions, not a generic GUI session unlock. [Apple FileVault deployment](https://support.apple.com/guide/deployment/intro-to-filevault-dep82064ec40/web).

### Linux

`loginctl unlock-session` explicitly asks a session that supports it to deactivate its screen lock. This is a promising *direct* operation for an existing session, but the actual effect belongs to the desktop lock implementation and the caller's access to the appropriate logind/session bus. Its presence does not imply pre-login greeter authentication. AUV's current Linux Portal capture and `/dev/uinput` input paths solve different problems. A target-specific proof should check the resulting lock state on GNOME and KDE separately, including which daemon identity may call it. [systemd loginctl](https://www.freedesktop.org/software/systemd/man/252/loginctl.html), [AUV Linux capture](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-driver-linux/src/capture.rs), [AUV uinput](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-driver-linux/src/native/uinput.rs).

## Decision gates for a concrete slice

1. Select the target state: existing locked session only, or also signed-out/preboot states.
2. Select who supplies OS-unlock authority: per-request credential, locally enrolled policy, or explicit elevation of paired Device trust.
3. Select one OS and desktop/session configuration. Validate native unlock and independent state readback *on that configuration* before adding a portable `DeviceService` claim.
4. For target-local credentials, define provisioning, store access identity, rotation, and trace exclusion before exposing the CLI command. Current generic `input.typeText` accepts literal CLI text and serializes it into invoke inputs, so it should not carry the secret. [AUV argument encoding](https://github.com/moeru-ai/auv/blob/2957b9ffeb5cdf6ce45b2173e866d7ed75726625/crates/auv-cli-invoke/src/command.rs).

## macOS 26.3 live probe (2026-09-27)

Evidence level: one live probe on an Apple Silicon spare Mac, not an unlock support claim. Over SSH, AUV 0.0.16 was installed but no daemon was running. A temporary AUV daemon started from the SSH session on a private Unix socket remained alive after the owner locked an already logged-in graphical session. The target reported `IOConsoleLocked=true` and `CGSSessionScreenIsLocked=true` through IORegistry; SSH and the daemon's `GET /apis/auv/daemon/v1/devices` continued to respond. This establishes request reachability while locked on this machine, not native input or unlock.

An `app.probePermissions` command started over SSH returned `accessibility=missing`, `screen_recording=missing`, `screen_capture_kit=unknown`, and `automation_to_system_events=granted`. A temporary Swift process started over SSH likewise reported `AXIsProcessTrusted() == false`. Reading login Keychain settings over SSH returned `User interaction is not allowed` both before and after locking. **Correction:** that invoke command did not have a root `--device-id` selection. Setting `AUV_CONTEXT` alone did not route this CLI command through the daemon; the permission result belongs to the SSH process and establishes nothing about a daemon-spawned Runner. These observations do rule out assuming that an SSH process can post privileged input or read an ordinary user Keychain item. They do not prove that an explicitly authorized graphical-session host or a different Keychain access group would behave the same way.

The initial test daemon and probe files are under `/tmp/auv-unlock-probe.wMbqtM`; the later GUI LaunchAgent test is under `/tmp/auv-unlock-agent.LunX3b` on the spare Mac. The next gate is a non-secret, native input probe from the actual host identity after the owner grants required macOS permissions. Only if that works at the lock UI should a target-local credential store and dedicated `DeviceService` unlock operation be implemented. AUV must still independently observe `IOConsoleLocked` changing to `false` after authentication; IORegistry lock keys are probe evidence rather than a promised public API contract.

After the owner granted Accessibility to `/Users/neko/.cargo/bin/auv`, `auv doctor` run in the graphical Terminal reported Accessibility, Screen Recording, and ScreenCaptureKit granted. A one-shot `auv doctor --json` running directly as a GUI LaunchAgent reported Accessibility granted. Several `app.probePermissions` calls started from SSH or Terminal without a root Device selector returned their respective process permissions; these were local operations regardless of the `AUV_CONTEXT` environment variable. A GUI LaunchAgent invocation without a root Device selector did not finish during the short probe and was stopped, so it yielded no permission conclusion.

The owner created a persistent `auv.core.local` Runner from graphical Terminal. Its identity remained stable across the local, unselected SSH permission command, but that command did not use the Runner. A correctly selected command using `AUV_ENDPOINT=unix:///tmp/auv-unlock-agent.LunX3b/daemon.sock auv --device-id <target-id> invoke app.probePermissions` created a daemon Run and did not finish during the short probe; it was canceled and the Run was explicitly stopped. Thus the actual Runner permission result remains **unknown**. Apple's [Security Server architecture](https://developer.apple.com/library/archive/documentation/Security/Conceptual/Security_Overview/Architecture/Architecture.html) explains why graphical authentication UI is unavailable to command-line or SSH sessions; the native target-side path still requires testing.

A correctly selected `display.list` invocation from SSH subsequently completed through the GUI LaunchAgent daemon and returned the built-in display. The earlier `display.list` timeout followed the blocked permission probe; its Run was canceled. A selected `input.key esc --no-overlay` invocation from SSH then returned `selected_path=foreground_system_events`, one successful posting attempt, and `verified=false` while the desktop was unlocked. This is delivery evidence only. A temporary `caffeinate -i -s` process (PID 30903) was started to keep the spare Mac reachable during the next lock probe; it and the temporary LaunchAgent need removal at the end of testing.

With the owner manually locking the same graphical session again, IORegistry reported `IOConsoleLocked=true` and `CGSSessionScreenIsLocked=true`. The correctly selected remote `input.key esc --no-overlay` command again returned one successful `foreground_system_events` posting attempt and `verified=false`; an immediate IORegistry readback still reported `IOConsoleLocked=true`. Esc cannot authenticate, so this neither proves nor disproves that the login UI received the event. Visual confirmation of a UI change was requested from the owner. No password was read, sent, or entered in this probe.

The temporary Runner, GUI LaunchAgent, SSH-started daemons, `caffeinate` process, agent plist, and named `/tmp/auv-unlock-*` probe directories were removed after the lock probe. The spare Mac remained locked when cleanup began. The paths above identify test artifacts during the probe and are no longer expected to exist.

The owner requested a second, visually watched input test. With `IOConsoleLocked=true`, a temporary selected-Device AUV call posted `input.key return` through `foreground_system_events` and returned `verified=false`; `IOConsoleLocked` remained true. The owner observed **no visible change** on the lock screen. This is negative evidence for the current `.cgSessionEventTap` foreground keyboard path on this Mac. The temporary daemon, `caffeinate`, and files for that test were removed.

As a narrower native control, a throwaway HID-tap probe was compiled on the spare Mac at `/tmp/auv-lock-hid-probe`. It checks Accessibility and Post Event consent, waits for `IOConsoleLocked=true`, then posts one Return key pair at `.cghidEventTap`. The owner ran it from graphical Terminal and obtained `accessibility=true post_event=true` and `posted Return at HID tap; effect unverified`. The owner reported that the password input **appeared** to gain focus. A separate, non-secret sequence probe then posted Return, `123456`, Return at the HID tap. Its output reported all key pairs posted and `lock_state_after=true`; the owner visually confirmed six password dots followed by a password-error message. This establishes keyboard delivery to the locked login UI and one failed authentication attempt on this Mac. It does not establish successful unlock or unattended secret availability.

A third throwaway local credential probe read the Mac login password with `readpassphrase` from the spare Mac's graphical Terminal, without echo or network transfer, before the owner manually locked the desktop. After the lock, it posted Return, Unicode credential events, and Return at `.cghidEventTap`. Its output reported `credential events submitted; checking lock state` and `unlock_observed=true`; the owner independently confirmed that the desktop unlocked. This is a **successful native unlock proof on one already logged-in macOS 26.3 session**, with a previously authorized graphical process and a secret held transiently in that process. It does not prove that a daemon/Runner can reach the HID tap, that a local secret store is readable while locked, that a remote request can trigger the operation, or that the same path works at a signed-out or FileVault preboot screen. The throwaway Swift program does not write the password to disk or logs, but Swift String storage is not guaranteed to be zeroized before its process exits.

A fourth throwaway remote-trigger probe held the locally entered password in the authorized graphical process, then created a mode-0600 FIFO in a private temporary directory after the owner locked the desktop. An SSH client under the same user identity sent one byte (`U`) to that FIFO; no password was sent. Just before the request, SSH read `IOConsoleLocked=true`; just after, it read `IOConsoleLocked=false`, and the probe process exited. The owner supplied terminal output including `remote request received`, `credential events submitted; checking lock state`, and `unlock_observed=true`. This establishes a remote request triggering the already proven target-local HID unlock path on this configuration. It is still a prototype transport, **not** an AUV DeviceService operation, persistent credential store, or production authorization policy. The FIFO, temporary `caffeinate` process, and probe binaries/sources on the spare Mac were cleaned up.

## macOS 26.3 signed-out feasibility gate (2026-09-28)

Evidence level: one throwaway native gate on the same spare M1 Pro Mac, **not** an AUV Device API or signed-out support claim. A uniquely named root LaunchDaemon and `LoginWindow` LaunchAgent were installed without altering the older `dev.auv.unlock-selected` job. The owner entered a login credential locally into a unique System.keychain item through a hidden Terminal prompt. The installed machine service returned `service_vault_read_ok` both before and after the owner logged out. After logout, SSH still reached that service, `/dev/console` belonged to `root`, and `who` showed no console user. These observations establish service lifetime and service-identity access to this persistent item in the tested signed-out state; they do not establish login delivery.

The LoginWindow agent started but reported `accessibility=false post_event=false`. A remote one-byte, non-secret `P` trigger caused it to post Return, and the owner visually observed the intended `neko` password field gain focus. Immediately before the only credential attempt, the service again passed its vault read check and independent reads still showed `root` with no console session. A one-byte `S` trigger then made the service read the local item and pass it over a root-only FIFO to the LoginWindow agent. The agent logged only that credential events were posted; the owner observed **no visible input or UI change**. After 30 seconds the service returned `outcome_unverified`, and `/dev/console` and `who` still showed no new user session. A one-attempt marker prevented retries.
