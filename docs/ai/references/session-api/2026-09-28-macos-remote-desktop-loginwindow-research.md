## What Apple documents

| Finding | Evidence level | Primary source |
| --- | --- | --- |
| ARD client settings offer an explicit choice to **start remote management at system startup**. Access and the `Control` privilege are configured separately; startup alone does not authorize control. | Documented product behavior | [Set access privileges for Remote Desktop](https://support.apple.com/en-au/guide/remote-desktop/apdfab787da/mac), [About access privileges](https://support.apple.com/en-gb/guide/remote-desktop/apd84ce53cb/mac) |
| ARD's `Send UNIX Command` works at the login window when run as root or another specified user. Apple says the “current user” choice fails there because no current user exists. This proves the remote management service has a signed-out system-level path; it does **not** by itself prove graphical keyboard input. | Documented product behavior | [Execute commands remotely with Remote Desktop](https://support.apple.com/en-is/guide/remote-desktop/apd91b63ef0/mac) |
| ARD can remotely log out the current user to return the target to its login window, and can control a client screen when the client grants `Control`. Apple does not explicitly say in these pages whether its graphical `Control` command can type into the login-window password field. | Documented product behavior; last sentence is an evidence limit | [Sleep, shut down, log out, or restart](https://support.apple.com/en-kw/guide/remote-desktop/apd5535ee19/mac), [About access privileges](https://support.apple.com/en-gb/guide/remote-desktop/apd84ce53cb/mac) |
| Screen Sharing is a separately configured macOS service for remotely viewing and controlling a Mac. It cannot be enabled at the same time as Remote Management. The built-in service and ARD are VNC compatible; macOS offers a setting to allow non-Apple VNC viewers to control the screen. | Documented product behavior | [Turn Mac screen sharing on or off](https://support.apple.com/en-md/guide/mac-help/mh11848/mac), [Virtual Network Computing access and control](https://support.apple.com/en-au/guide/remote-desktop/apde0dd523e/mac) |
| Apple warns that third-party VNC viewers may transmit keystrokes without encryption, and advises that the separate VNC password must differ from local and administrator passwords. VNC control is therefore a distinct authorization and security decision, not a drop-in credential path. | Documented security constraint | [Virtual Network Computing access and control](https://support.apple.com/en-au/guide/remote-desktop/apde0dd523e/mac) |
| Modern `SMAppService` distinguishes login items/agents, which bootstrap on user login, from an approved LaunchDaemon, which bootstraps on each boot. Apple’s older process guide says system daemons continue when no user is logged in, but have no WindowServer GUI access; user agents have GUI access while their user session is active. | Documented platform architecture; older guide should be read with modern API docs | [SMAppService registration](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [Designing Daemons and Services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/DesigningDaemons.html) |
| Apple describes `loginwindow` as coordinating both the visible authentication screen and creation of the authenticated user environment. It separately describes the root session and login sessions. This is why a root network service can remain available while an ordinary user's GUI helper ends at logout. | Documented platform architecture, from archived programming guides | [The Life Cycle of a Daemon](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/Lifecycle.html), [Root and Login Sessions](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPMultipleUsers/Concepts/SystemContexts.html) |
| FileVault **preboot unlock** and the ordinary macOS login window are separate stages. The user’s recent experiments were at the latter, after a normal logout. ARD startup support should not be extrapolated to an encrypted-volume preboot prompt. | Documented distinction; applicability is an inference from the experiment state | [Use Login Window Mode with FileVault](https://support.apple.com/en-ie/102001), [FileVault and smart card usage](https://support.apple.com/en-au/guide/deployment/dep806850525/1/web/1.0) |

## What open-source remote desktop implementations show

| Implementation | Source-level mechanism | Evidence limit |
| --- | --- | --- |
| Chromium Remote Desktop | Its [LaunchAgent](https://chromium.googlesource.com/chromium/src/+/HEAD/remoting/host/installer/mac/LaunchAgents/org.chromium.chromoting.plist) loads in both `Aqua` and `LoginWindow`; the installed helper starts the host in that graphical context ([host service source](https://chromium.googlesource.com/chromium/src/+/HEAD/remoting/host/mac/host_service_main.cc)). The host embeds a Mach-O `__CGPreLoginApp,__cgpreloginapp` section and says this permits login-screen input ([host source](https://chromium.googlesource.com/chromium/src/+/HEAD/remoting/host/remoting_me2me_host.cc)); its [keyboard injector](https://chromium.googlesource.com/chromium/src/+/HEAD/remoting/host/input_injector_mac.cc) posts `CGEvent` at the session event tap. | This is a first-party description of Chromium's design, not a verified sign-in on the spare Mac or a public Apple guarantee. |
| RustDesk and Deskflow | RustDesk has a [root service](https://github.com/rustdesk/rustdesk/blob/master/src/platform/privileges_scripts/daemon.plist), an [Aqua/LoginWindow agent](https://github.com/rustdesk/rustdesk/blob/master/src/platform/privileges_scripts/agent.plist), and the same [Mach-O linker section](https://github.com/rustdesk/rustdesk/blob/master/.cargo/config.toml#L7-L10). [Deskflow's macOS source](https://github.com/deskflow/deskflow/blob/master/src/lib/platform/OSXScreen.mm#L47-L51) also embeds that section. | The section is not sufficient evidence of reliable character entry: a [RustDesk issue](https://github.com/rustdesk/rustdesk/issues/11802) reports Return reaching a Mac **lock-screen** password field while characters fail. This is analogous evidence, not a signed-out LoginWindow test; the report also does not isolate the build or input path. |
| MeshCentral macOS agent fork | The fork's [input implementation](https://github.com/stanelie/meshcentral-mac-agent/blob/main/agent/mac_events.c) routes `loginwindow` keys and mouse input through localhost RFB/VNC to Apple's `screensharingd`, while using `CGEvent` in an ordinary Aqua session. Its [architecture note](https://github.com/stanelie/meshcentral-mac-agent/blob/main/docs/architecture.md) describes this as a workaround for failed prelogin input. | The route and its success are the fork author's implementation claims, not an Apple API contract. Its RFB 3.3 handshake supports VNC password authentication and accepts a server-advertised no-auth mode, so it cannot be treated as an already secure AUV transport. Apple's binary does carry a private HID dispatch entitlement, as checked below. Apple documents [Screen Sharing control and its access settings](https://support.apple.com/en-md/guide/mac-help/mh11848/mac), but not this internal routing. Enabling VNC also changes the host's authentication and network exposure. |

Apple's own [IOHIDFamily build project](https://github.com/apple-oss-distributions/IOHIDFamily/blob/main/IOHIDFamily.xcodeproj/project.pbxproj#L18622-L18629) uses `-sectcreate __CGPreLoginApp __cgpreloginapp /dev/null` for `hidd`. This corroborates that the marker is intentional platform behavior. It remains an undocumented internal mechanism with no published compatibility promise for third-party signed helpers. A read-only `otool -l` check of the first two AUV signed input-gate binaries found **no** `__CGPreLoginApp` segment. A later one-shot helper added exactly that marker while keeping the prior Unicode event and HID tap, and still produced no visible password dot after a successful physical-key control. The marker alone is therefore insufficient in the tested macOS 26.3 setup. Chromium also used the session event tap, while the AUV gates posted at the HID tap; that difference remains untested.

Read-only inspection of the **local macOS 26.3 system binaries**, not a live remote-control test, adds a second Apple implementation fact. `/System/Library/LaunchDaemons/com.apple.screensharing.plist` defines a VNC listener and starts `screensharingd`; `/System/Library/LaunchAgents/com.apple.screensharing.agent.plist` permits `ScreensharingAgent` in both `Aqua` and `LoginWindow`. `codesign -d --entitlements -` shows `screensharingd` has `com.apple.private.hid.client.event-dispatch` (as well as other private HID client entitlements). `otool -l` shows the prelogin Mach-O marker in `ScreensharingAgent`, but not in `screensharingd`. These OS-installed files support the fork's claim that Apple's service has an input privilege absent from the AUV probes; they do not reveal the exact internal dispatch sequence or authorize AUV to call that private interface. The installed `man screensharingd` says the service is enabled through Screen Sharing or Remote Management, consistent with [Apple's configuration guide](https://support.apple.com/en-md/guide/mac-help/mh11848/mac).

## Mechanism we can and cannot establish

The defensible high-level model is: an administrator enables a system-started, authenticated remote service; the service accepts a separately authorized control connection; macOS owns the login window and authentication transition. The first two parts are directly supported by Apple’s ARD and launchd documentation. The details of how Apple’s screen-sharing server routes a remote key to `loginwindow` are **not published in the sources found here**. The MeshCentral fork suggests one route through Apple's server, while other projects mark their own binary for prelogin event posting. Neither establishes a supported AUV API.

The AUV gates tested a different path: a signed LoginWindow helper with Accessibility and Post Event permission posted Core Graphics keyboard events. A physical `1` produced one password dot in each of two controlled comparisons; a virtual keycode `1`, a Unicode override `1`, and the same Unicode override from a marker-bearing helper produced no dot. This is target evidence that the tested `CGEvent` path failed at the password field, not proof that macOS cannot support remote login or that the secure field always rejects synthetic input. Apple’s [`CGEvent.post(tap:)`](https://developer.apple.com/documentation/coregraphics/cgevent/post%28tap%3A%29) describes posting an event, not an application-level acknowledgment that `loginwindow` accepted a character. The specific filtering/dispatch point remains unobserved.

## Consequence for AUV

1. Keep macOS signed-out native `Device` entry **unsupported** on current evidence. The user-observed login-window character is the decisive missing gate, despite a surviving root service, readable target-local keychain item, signed helper, and positive TCC booleans.
2. The source-backed prelogin marker difference has now been isolated and failed the visible-input gate. Examine the remaining session-event-tap difference and Apple's Screen Sharing / ARD service boundary before another input experiment. A marker-based helper remains dependent on undocumented OS behavior. A VNC-based client would need an explicit secure transport, target authorization, session selection, input/output verification, and FileVault boundary. Neither is implemented or supported by documentation alone.
3. A future gate should make one mechanism-specific prediction, use only a harmless character first, and independently verify its visible effect before any target-local credential attempt. For Screen Sharing / ARD, first establish ordinary signed-out control under a user-approved configuration without automation of the password. For a custom helper, isolate the session event tap from the failed HID-tap binaries. No new logout is required to preserve the current unsupported conclusion.
