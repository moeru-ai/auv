# Background input, AX trees, and media capture: gap review

> NOTICE: This source review records historical revisions. The [Wayland background input research](2026-09-13-wayland-background-input-research.md) records the 2026-09-13 decision, later implementation PRs, and evidence boundaries. Candidate rows do not authorize implementation.

Date: 2026-09-09. Classification: docs-only research.

Two independent reviewers examined background input and AX. The lead reviewer examined native audio and video implementations. The review used source code only. It included no GUI receiver, audio, or screen recording tests. Source implementations do not establish behavior across OS versions.

The background input, AX, and media tables use the same nine columns. BG/AX/MEDIA identifiers retain the links to earlier discussions. A group can contain several actions. Each issue still needs the smallest scope with independent acceptance criteria.

This review supplements the [31-candidate inventory](2026-09-09-computer-use-improvement-candidates.md). It contains eight background input groups, seven AX groups, and one conditional AX extension. Most groups refine existing candidates and do not increase the bug count. MEDIA-1 through MEDIA-3 are three new, independent capability candidates. The owner did not authorize their implementation.

AUV has PID/window-targeted delivery on macOS. Windows has window-targeted click/wheel messages without foreground activation. Actual consumption still depends on the target toolkit. Linux/Wayland window click/wheel rejects BackgroundOnly and permits foreground Portal fallback.

All three platforms have accessibility tree foundations. The main gaps concern exact targets, state admission, result evidence, actionable nodes, and script access. Public implementations for general video recording, microphone capture, and system output audio capture remain absent. The oh-my-pi AudioCapture implementation captures the default input device or microphone. It does not establish system output loopback support.

The background input and AX sections identify their fixed revisions. The audio review also examined oh-my-pi remote main `856d9375e08dfe79d5e7470e8b92840f1eae772a`. Its `pi-natives/src/audio.rs` and `pi-voice/src/audio.rs` files exactly match revision `a33cc26824e3c91edd9fa42d681f10dceb4ac2f0`. The OMP AX references retain that earlier a33 revision. This review does not claim a complete desktop code review of the newer main. These gaps do not all correspond to recent upstream additions.

The original priorities remain: P1 covers current correctness, evidence, and access to existing capabilities. P2 covers capability improvements with consumers. P3 covers optional extensions. Difficulty is M for medium, L for high, and XL for complex cross-platform changes. These estimates include acceptance evidence for the smallest useful scope, but no schedule.

For P1 risks, the next step is evidence or reproduction. A risk does not automatically authorize P1 implementation. AX-6 separates P1 evidence from P2 conditional implementation. Enablement and cache behavior require a real consumer, reproduction, and evidence across versions. AUV retains InputActionResult and separate verification. Retired candidate promotion and an aggregate runtime crate remain outside the scope.

Reference boundaries:

- BG-1: CUA also explicitly rejects background modifier-click on Windows.
- BG-2: An SPI authentication envelope is not a universal macOS/toolkit correction. AUV already has a single-route PidTargeted alternative.
- BG-3: CUA defines refusals for hidden/minimized/off-Space states, unresolved AX targets, and keyboard targets with multiple windows under one PID.
- BG-4: The CUA Rust guard includes only the reactive layer. Focus restoration does not prove zero disturbance.
- BG-5: UIA S_OK can produce no visible effect.
- BG-6: AUV already has a mouse-motion mutex and clipboard lock. Concurrency control is not wholly absent.
- BG-7: AUV has historical live application evidence. Reference fixtures do not establish support across all versions. Contract-compliant refusal is not execution capability.
- BG-8: macOS-only Peekaboo is not a baseline for cross-platform capability counts.

### How much remains

AUV already has basic macOS background delivery. The remaining work concerns **eight engineering boundaries**, most of which the original table covers. This review expands modifier-click, toolkit-specific keyboard authentication envelopes, state admission, focus disturbance observation/suppression, and the Windows semantic ladder. Reliable evidence for the recipient and side effects is harder than parameter integration.

The evidence does not support a completion percentage. No comparison used identical macOS/Windows versions, fixtures, window states, and success criteria. Relevant states include foreground, occluded, minimized, and off-Space windows. CUA explicitly rejects many background states. Peekaboo held-pointer input has left/right, exact-window, and duration limits. Neither project provides unconditional background automation.

Suggested minimum acceptance procedure:

1. Record click down/up/count+modifier in independent AppKit/Electron receivers. Make sure that a single click produces exactly one pair. Make sure that triple clicks obey the contract. Record side effects for None and explicit-fallback policies.
2. Use two windows under one PID, with focus on one window. Make sure that a request for window B does not silently change A. After refusal, make sure that both windows remain unchanged.
3. Define allow/refuse behavior for visible-unfocused, occluded, minimized, hidden, and off-Space states. Define raw pointer, raw key, and semantic AX cases separately. Do not require every case to pass.
4. Run actions while the user moves the mouse and switches applications. Record focus/cursor evidence before, during, and after each action. Do not describe restoration as zero disturbance.
5. Include prefix injection failure, cancellation, and parallel operations under one PID. Make sure that no blind full-text replay occurs. Make sure that results include completed/unknown progress.

The eight groups do not justify eight additional OS issues. Existing OS mappings remain the baseline. Only new parameters, platform actions, or admission contracts need additional candidate scopes.

Reference boundaries:

- AX-1: OMP window_root uses title/frame and a unique-title fallback. This does not establish strict window identity. Current/previous-generation references are not permanently stable.
- AX-2: The model needs native facts rather than only the common minimum.
- AX-3: OMP defaults unknown enabled to true. This behavior is unsuitable as a model. AUV already has value and diagnostic access to some actions/attributes.
- AX-4: OMP children has no cursor pagination. Query results discard completeness information. Attribute strings truncate at 200 characters.
- AX-5: One native timeout is not an end-to-end deadline. Some CUA depth-cutoff branches do not set truncated.
- AX-6: Numeric PID caches in OMP/KWWK require consideration of process reuse. The KWWK no-op observer enables AX, rather than a tree-change stream.
- AX-7: OMP Unit results do not fit the AUV contract. AUV retains InputActionResult and separate verification.
- AX-8: Peekaboo establishes window geometry/lifecycle notifications and polling fallback only. It does not establish general AX tree diffs.

AX-1 app/window/ref identity is a prerequisite for BG-3 admission and AX-7 actions. AX-3/5 make observations interpretable. AX-6 requires evidence before side effects, regardless of enablement in other frameworks. BG-7 provides shared receiver evidence for BG-2/3/6. BG-5 and AX-7 need one implementation candidate for the same specific control consumer.

The proposed sequence starts with minimum evidence for ambiguous identity, unknown/truncated states, background consumption, and Chromium cold starts. Results then guide contract corrections and integration with real consumers. Separate media recording/capture changes connect to run artifacts. Each new implementation needs a concrete consumer and explicit acceptance criteria. Retired candidate promotion and a new aggregate runtime crate remain outside the scope.

MEDIA-1 minimum acceptance procedure:

1. Select one exact target.
2. Record a known animation.
3. Decode the video.
4. Make sure that frames and timing match the expected animation.
5. Include normal stop, cancellation, and encoding failure cases.
6. Make sure that each artifact is readable or explicitly incomplete.
7. Make sure that the recording correlates with the run timeline.
8. Do not use file existence as a completeness test.

MEDIA-2 minimum acceptance procedure:

1. Produce a known application tone with a silent microphone.
2. Make sure that capture uses the specified output.
3. If the contract promises application scope, produce sound from another application simultaneously.
4. Make sure that capture excludes that other application.

MEDIA-3 minimum acceptance procedure:

1. Use a controlled input fixture.
2. Make sure that the sample rate and order match the fixture.
3. Make sure that repeated stop releases the device.

Cross-thread consumption requires bounded buffers and evidence of lost samples. Independent audio capture does not justify an aggregate scheduler for future audio/video synchronization.
