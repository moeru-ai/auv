# Login-screen capture and input: Windows and Linux source review

Date: 2026-09-27. Scope: RustDesk, Sunshine, Parsec, and platform APIs. This is source and documentation evidence, not an AUV support claim or a local end-to-end validation.

## Windows: feasible with a privileged host in the target session

- **Capture:** Microsoft says `IDXGIOutput1::DuplicateOutput` returns `E_ACCESSDENIED` without access to the current desktop image, and specifically says only an application running as `LOCAL_SYSTEM` can access the secure desktop. It also documents `DXGI_ERROR_UNSUPPORTED` around desktop/mode switches, which requires recreating duplication after the switch. [Microsoft Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput)
- **Session placement:** Services cannot directly interact with a user since Vista; Microsoft prescribes a process in the interactive session, launched with `CreateProcessAsUser`. The token's session ID and desktop/window-station access matter. A service running in Session 0 is insufficient on its own. [Microsoft Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw)
- **Sunshine implementation:** Its service duplicates its own LocalSystem token with `DuplicateTokenEx`, changes `TokenSessionId` to `WTSGetActiveConsoleSessionId()` with `SetTokenInformation`, and calls `CreateProcessAsUserW` to launch `Sunshine.exe` in that session. It restarts the process on console-session changes. Its capture path calls `OpenInputDesktop` / `SetThreadDesktop` before `IDXGIOutput5::DuplicateOutput1` or `IDXGIOutput1::DuplicateOutput`. [Sunshine service](https://github.com/LizardByte/Sunshine/blob/master/tools/sunshinesvc.cpp), [desktop binding](https://github.com/LizardByte/Sunshine/blob/master/src/platform/windows/misc.cpp), [DXGI capture](https://github.com/LizardByte/Sunshine/blob/master/src/platform/windows/display_base.cpp)
- **RustDesk implementation:** Its Windows service tracks the active session and launches a privileged `--server` process there. Input and capture paths call `try_change_desktop`; the native implementation compares the thread desktop with `OpenInputDesktop` and switches via `SetThreadDesktop`. RustDesk uses `SendSAS` for the special Ctrl+Alt+Del path; this is distinct from ordinary key injection. [RustDesk Windows service and SAS](https://github.com/rustdesk/rustdesk/blob/master/src/platform/windows.rs), [native desktop switch](https://github.com/rustdesk/rustdesk/blob/master/src/platform/windows.cc), [input call sites](https://github.com/rustdesk/rustdesk/blob/master/src/server/input_service.rs)
- **Parsec product evidence:** Its per-computer installation permits Windows login-screen access. Its service permits capture and input on lock screen and UAC; Parsec documents `parsecd.exe` under both SYSTEM and the logged-in user, plus `pservice.exe` under SYSTEM. Parsec is closed source here, so its exact capture and input API choices are **not established** by this evidence. [Parsec Windows app/service](https://support.parsec.app/hc/en-us/articles/32381199341716-Parsec-App-for-Windows), [installation modes](https://support.parsec.app/hc/en-us/articles/32381368159124-Install-Parsec-App-on-Windows)
- **SAS:** `SendSAS` has its own Windows policy (`SoftwareSASGeneration`) and service requirements. RustDesk currently temporarily sets this registry policy to allow service-generated SAS; AUV should treat this as a separately authorized capability, not synthesize Ctrl+Alt+Del with ordinary keys. [RustDesk `send_sas`](https://github.com/rustdesk/rustdesk/blob/master/src/platform/windows.rs), [Microsoft policy](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-winlogon#softwaresasgeneration)

**AUV implication (inference):** A Windows login-screen feature would require an installed LocalSystem service and a session-scoped privileged capture/input worker. It must detect active-session and input-desktop changes, recreate DXGI duplication, bind the worker thread to the current input desktop, and report whether capture and delivery succeeded separately. Existing ordinary per-user window capture/input is not evidence for this capability. Validate lock screen, pre-login Winlogon, UAC secure desktop, console switching, RDP sessions, and display-mode changes independently.

## Linux: compositor/session model decides the path

- **Sunshine:** Its documented Linux methods include X11/XCB, Wayland compositor methods, portal, and DRM/KMS. KMS requires `CAP_SYS_ADMIN`; its standard Linux service is a *user* systemd service, and `/dev/uinput` permission is configured for virtual input. These capabilities alone do **not** establish that its standard user service runs before login or handles a greeter. [Sunshine capture configuration](https://github.com/LizardByte/Sunshine/blob/master/docs/configuration.md), [installation/service/input setup](https://github.com/LizardByte/Sunshine/blob/master/docs/getting_started.md), [KMS source](https://github.com/LizardByte/Sunshine/blob/master/src/platform/linux/kmsgrab.cpp)
- **RustDesk Wayland:** Ordinary PipeWire/`xdg-desktop-portal` capture requires an active user session and consent; it cannot by itself serve the Wayland greeter. RustDesk's newer optional DRM/KMS backend bypasses the portal; a separate privileged path obtains scanout, while input uses kernel `uinput`. A first integration incorrectly rejected the greeter and routed input to X11; the linked fix reports actual **SDDM Plasma Wayland** greeter rendering, ASCII password typing, and absolute click on a 2880×1800 panel. It explicitly does **not** prove GDM or non-ASCII password input. [RustDesk DRM design discussion](https://github.com/rustdesk/rustdesk/discussions/15417), [greeter failure and validation](https://github.com/rustdesk/rustdesk/issues/15791), [display service](https://github.com/rustdesk/rustdesk/blob/master/src/server/display_service.rs)
- **Kernel input API:** `/dev/uinput` lets a privileged/authorized process create a virtual keyboard and pointer by setting event bits, issuing `UI_DEV_SETUP`/`UI_DEV_CREATE`, then writing input events. The greeter compositor must discover and accept that device and the coordinate mapping must match the actual display geometry. [Linux kernel uinput documentation](https://github.com/torvalds/linux/blob/master/Documentation/input/uinput.rst)

**AUV implication (inference):** For a Linux pre-login Wayland greeter, a system-level lifecycle plus an authorized KMS capture mechanism and `/dev/uinput` delivery is a plausible path. The capture broker, display-manager session detection, compositor geometry, seat routing, keyboard layout, and lock-to-login transition all need explicit validation. For X11 greeters, X server authorization and display-manager environment are separate requirements; user-session `$DISPLAY`/`$XAUTHORITY` cannot simply be reused. Portal-based user-session support should not be counted as pre-login support.

## Evidence level and decision boundary

Windows has official API requirements plus two open-source host implementations and Parsec's product claim. Linux has an upstream RustDesk SDDM Wayland greeter test report and source path, with GDM and non-ASCII input unproven. Neither platform has been validated in AUV by this note. The concrete next slice, if approved, is a platform-specific feasibility probe with typed capture and input results at the existing driver boundary, not a new cross-platform login-screen abstraction.
