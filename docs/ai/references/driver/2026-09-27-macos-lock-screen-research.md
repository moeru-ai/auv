# macOS lock-screen and login-window capture/input research (2026-09-27)

Status: research, not an AUV capability claim. This note separates documented APIs, product evidence, and hypotheses requiring a device probe.

## State boundaries

| State | What is running | Evidence and implication |
| --- | --- | --- |
| Existing user session, screen locked | The macOS user GUI session remains available | Apple explicitly describes screen-sharing/remote-control software observing a locked screen. This is the smallest AUV probe. [Apple lock-screen notice](https://support.apple.com/en-us/120315) |
| OS booted, `loginwindow`, no user logged in | A distinct graphical login session | Apple DTS says a global LaunchAgent with `LimitLoadToSessionType=LoginWindow` runs there as root and can talk to WindowServer; ordinary Aqua agents run in logged-in GUI contexts. A system LaunchDaemon alone has a global context, not a GUI context. [Apple DTS on launchd contexts](https://developer.apple.com/forums/thread/696859), [TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html) |
| Restart with FileVault still locked | Pre-boot unlock, before the ordinary macOS user/session stack | Apple says credentials are required during boot. Parsec requires FileVault disabled for its login-screen installer. Thus do **not** infer that an ordinary LaunchAgent or ScreenCaptureKit can capture this screen. On Apple silicon running macOS 26+, Apple documents a separate **SSH FileVault unlock** feature when Remote Login and a suitable network are available; that is not screen capture or GUI input. [Apple FileVault deployment](https://support.apple.com/en-hk/guide/deployment/dep82064ec40/web), [Parsec login-screen requirements](https://support.parsec.app/hc/en-us/articles/32381618319124-Access-Login-Screen-on-macOS) |

## Public API and process pieces

- **Capture:** AUV already uses `ScreenCaptureKit` (`SCShareableContent` and screenshot capture) in [Capture.swift](../../../../crates/auv-driver-macos/native/swift/Sources/AuvMacosNative/Capture.swift). Apple calls ScreenCaptureKit the modern capture API and requires screen recording authorization. Use `SCShareableContent`, `SCContentFilter`, `SCScreenshotManager` or `SCStream` for a display, subject to empirical loginwindow testing. `CGPreflightScreenCaptureAccess()` checks the ordinary Screen Recording authorization; `CGRequestScreenCaptureAccess()` requests it. [Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit), [Apple DTS capture API guidance](https://developer.apple.com/forums/thread/839069)
- **Unattended capture authorization:** Apple documents the restricted `com.apple.developer.persistent-content-capture` entitlement for VNC apps needing persistent capture; it requires an Apple request and approval. The documentation does **not** assert that this alone enables capture of `loginwindow`, so that remains a probe/Apple DTS question. [Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.persistent-content-capture)
- **Input:** Core Graphics `CGEventCreateKeyboardEvent`, `CGEventCreateMouseEvent`, `CGEventPost` (potentially at `kCGHIDEventTap` rather than a user-session tap) are the direct public candidate APIs. Apple defines the HID tap as where events enter WindowServer and `kCGSessionEventTap` as entering a login session. `CGPreflightPostEventAccess()` / `CGRequestPostEventAccess()` expose posting authorization. A successful post call is **not evidence** that `loginwindow` accepted the keystroke; test actual password-field focus, text entry, and login separately. [Apple event-tap locations](https://developer.apple.com/documentation/coregraphics/cgeventtaplocation/cghideventtap), [Apple Core Graphics functions](https://developer.apple.com/documentation/coregraphics/core-graphics-functions), [Apple DTS on event-posting consent](https://developer.apple.com/forums/thread/103992)
- **Permissions:** Screen Recording and event posting are separate privacy services. Apple’s PPPC payload describes Post Event as allowing CGEvents while its Screen Recording entry is worded as denying access; do not promise silent MDM pre-grant of capture. Capture and input grants should be established while a human can authorize them, using a stable signed app identity. [Apple PPPC payload](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web), [Apple ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit)
- **Lifecycle:** A privileged service can own durable transport/authentication, while a signed GUI-context agent owns WindowServer capture and input. A separate `LoginWindow` LaunchAgent and Aqua user agent may be needed at session transitions; their permissions and responsible-process identity require testing. Apple DTS establishes the launchd context rule, not capture success. [Apple DTS](https://developer.apple.com/forums/thread/696859)

## AUV implementation hypothesis and evidence gate

This would be a new owner-approved driver/lifecycle feature, not a patch to current app-local commands. Reuse the existing typed capture and `InputActionResult` paths; attach a session-context classification and report authorization/capture/input failures rather than claiming semantic login success.

1. First probe the **already logged-in locked session** with current signed AUV build and permissions. Verify captured pixels contain the lock screen; post a harmless key or click; then use a test account to verify credential entry only on a dedicated machine. Preserve frame, event result, session state and OS version as artifacts.
2. For **cold boot to loginwindow without FileVault preboot lock**, package a signed helper as `/Library/LaunchAgents` with `LimitLoadToSessionType=LoginWindow`, coordinated with a service and a normal Aqua agent. Probe capture API availability, TCC identity, event delivery, handoff after login, fast user switching, and reconnect. Treat `CGEventPost` success and captured frames as separate evidence.
3. For **FileVault preboot**, define an explicit unsupported GUI-capture/input result unless Apple documents or a controlled probe demonstrates a supported path. macOS 26+ SSH unlock is a distinct capability and should not be folded into AUV’s screenshot/input API.

Important uncertainty: neither Apple’s ScreenCaptureKit docs nor its persistent-capture entitlement page explicitly guarantees third-party capture of the LoginWindow context. A 2026 [RustDesk user report](https://github.com/rustdesk/rustdesk/discussions/15364) alleges macOS 26 TCC responsible-process failures for LaunchAgent capture, but another participant reports success. Treat this as a test matrix item, not a platform fact.
