## Priority and difficulty

Priority reflects correctness in the current AUV core, connections to existing capabilities, and value for actual consumers. It does not express vulnerability severity or implementation approval.

| Label | Meaning |
| --- | --- |
| P1 | First candidates for current correctness, reliable evidence, or reusable connections to existing capabilities. Risks need reproduction first. |
| P2 | Later API/model changes for existing scenarios. These need a prerequisite contract or an explicit application consumer. |
| P3 | Optional host/application extensions. The current core does not need them solely for feature parity. |
| S · Low | Local configuration/mapping with existing models and tests. No new native lifecycle. |
| M · Medium | One minimal operation or platform change. It can cross Rust/proto/JS but mainly reuses existing implementations. |
| L · High | New native semantics, lifecycle, concurrency, or real-application fixtures. Evidence must cross component boundaries. |
| XL · Very high | Multiplatform consistency or broad host/resource management. This requires smaller changes, not one default implementation scope. |

Difficulty includes the smallest meaningful acceptance evidence. It is not a line-count estimate or schedule promise. M does not mean three platforms in one change. For OS-26, the unit contract/adapter is one M, and later RPC/SDK access is another M. OS-22 starts with Windows at M, while two-platform alignment is approximately L. OS-27 starts with one rich format at M, while all platforms can reach L/XL.

Without an actual control consumer, OS-24 changes from P2 to P3. OS-31 remains P3 for an optional app.open consumer.

This review reassesses OS-01–20 and adds OS-21–31. OS-25–31 cover parameters and atomic APIs. OS-21–23 cover models, errors, and platform semantics. OS-24 covers combined execution boundaries. OS-09 also includes the Windows activation result with its bundle-ID shape. That example is not a separate architecture gap.

## Scope and dependencies of new candidates

- OS-21 reuses FailureCode/DriverError conversion and corrects error projection in one legacy helper. It differs from OS-12 action effects/verification. No parallel error system is necessary.
- OS-22 concerns observation completeness at the producer. OS-04/14 concern reference identity. OS-12 concerns verification consumers. These depend on each other but have different acceptance criteria. CUA currently marks only node-cap truncation. Its depth limit remains incomplete.
- OS-23 preserves raw platform probes and separates interface availability from authorization evidence. Operation preflight derives from decision facts of actual operations. It does not restore a static daemon capabilities table. Reflection retains service discovery.
- OS-24 studies one focus→type combination with framework serialization, stepwise verification, and retained completed prefixes after failure. It is not atomic commit/rollback for arbitrary batches. The Peekaboo reference uses AX focus, not an automatic extra mouse click.
- OS-25 reuses MouseButton. OS-26 defines units before scroll exposure. CUA approximates line/page units with pixels, without equal visual-distance guarantees across operating systems.
- OS-27 separates ClipboardSnapshot/ClipboardContent as concepts. Final names remain provisional until concrete design approval. Backups need platform/format-version boundaries. Existing rich preservation remains required.
- OS-28 starts with setFrame and reuses WindowMutationResult/readback. It differs from OS-09 route differences for the same command. Later move/minimize operations can connect separately. No native backend rewrite is necessary.
- OS-29/30/31 cover menu paths, standard file panels, and application open/readiness. Each is a separate consumer-led extension. This table does not authorize implementation.
- Windows app.activate exposes a macOS bundle-ID concept in its result. OS-09 includes this concrete platform-model gap. Platform identifiers retain their distinct meanings. Process names and bundle IDs are not one arbitrary string type.

## Suggested implementation order

1. **Establish a reliable baseline: OS-10 and OS-11.** Select existing owning tests first. Add a few independent receiver fixtures that establish input consumption.
2. **Reproduce and correct narrow failures: OS-01, OS-02, OS-03, OS-05, and OS-06.** Use one trigger per failure. Preserve compatibility requirements with established evidence.
3. **Connect the current core to scripts: OS-09, OS-13, and OS-17.** Make existing execution paths and capabilities consistently accessible first.
4. **Use concrete Windows consumers: OS-14, OS-15, and OS-16.** Do not use the complete UIA Pattern list as the next implementation scope.
5. **Select other candidates from actual scenarios.** OS-07/08/18/19 each have lifecycle and unknown-outcome boundaries. OS-20 is an optional application change. OS-04/12 expand only through actual observe/action/verification consumers.

Among new candidates, OS-21/22/25/26 take priority. OS-23/27/28 can connect with their existing consumers. OS-24/29/30/31 first need an actual application scenario, then a bounded change. Acceptance boundaries determine dependencies. P1 does not authorize default-behavior changes without reproduction or a contract decision.

These priorities, difficulty estimates, and ordering are research recommendations. This research changed no production code, ran no framework behavior tests, and created no Git commit.

The [background input, AX tree, and audiovisual capture review](2026-09-09-background-ax-and-media-gap-review.md) separates existing risks further. It also lists new MEDIA-1–3 capability candidates. Most BG/AX groups overlap existing candidates. They do not increase the bug count.
