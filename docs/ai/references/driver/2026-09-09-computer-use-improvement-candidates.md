## 优先级与难易度

优先级是按 AUV 当前 core 的正确性、已有能力接通与实际消费者价值给出的建议，不是漏洞严重级别，也不代表实施批准。

| 标记 | 含义 |
| --- | --- |
| P1 | 先处理：当前正确性、可信证据或高复用的已有能力接通；风险项先复现 |
| P2 | 后续选择：已有场景的 API/模型完善；依赖前置契约或明确 app consumer |
| P3 | 可选扩展：需要新的宿主或应用需求，当前 core 不必为了追平而实现 |
| S · 低 | 局部配置/映射，复用既有模型和测试，无新增原生生命周期 |
| M · 中 | 一个最小操作或单平台切片；可能跨 Rust/proto/JS，但主要复用现有实现 |
| L · 高 | 新原生语义、生命周期、并发或真实应用 fixture；需要跨边界验证 |
| XL · 很高 | 多平台一致性或大范围宿主/资源治理；应拆分，不作为当前单项默认范围 |

本表难度包含最小有意义验证，不是行数估计或工期承诺。M 不代表一次实现三平台；例如 OS-26 先完成单位契约/adapter，随后 RPC/SDK 接通另计一个 M；OS-22 先 Windows 为 M，双平台统一约 L；OS-27 先一种富格式为 M，全平台可能 L/XL。OS-24 无实际控件消费者时由 P2 降为 P3。OS-31 目前按可选 app.open 消费者列 P3。

原 OS-01～20 全部补评；本轮增加 OS-21～31。参数与原子 API 主要见 OS-25～31；模型/错误/平台语义见 OS-21～23；组合执行边界见 OS-24。OS-09 补入 Windows activation 被 bundle-ID 结果形状阻挡的例子，不重复计为一条架构缺口。

## 新增项的范围与依赖

- OS-21 复用已有 FailureCode/DriverError 转换，修一个 legacy helper 的错误投影；不同于 OS-12 的 action effect/verification，不新增平行错误体系。

- OS-23 保留平台原始 probe，将接口可用与授权证据分开；从真实 operation 的 decision facts 派生 preflight。不能退回 daemon 静态 capabilities 大表，Reflection 仍承担服务发现。
- OS-24 只研究一个 focus→type 组合：框架内不交错、逐步验证、失败保留已执行前缀。它不是任意 batch 的原子提交/回滚；Peekaboo 参考路径用 AX focus，不是自动多发一次鼠标 click。
- OS-25 复用 MouseButton。OS-26 补单位之后再暴露 scroll；CUA line/page 有像素近似，不能承诺跨 OS 视觉滚动量相等。

- OS-28 先接通 setFrame，复用现有 WindowMutationResult/readback；与 OS-09 的同名命令路由差异不同。后续 move/minimize 等逐项接通，不需要重写 native backend。
- OS-29/30/31 分别是菜单路径、标准文件 panel、应用 open/readiness，都是独立消费者驱动的能力扩展，不由本表自动授权实现。
- Windows app.activate 的输出包含 macOS bundle-ID 概念，是具体平台模型暴露问题，已并入 OS-09。保留平台标识的类型含义，不把 process name 与 bundle ID 混为一类任意字符串。
