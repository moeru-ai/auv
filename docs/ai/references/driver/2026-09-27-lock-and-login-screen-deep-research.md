# Lock and login screen capture/input: deeper source review

Date: 2026-09-27. Status: research only; no AUV lock-screen test or support claim. This note extends the three same-day platform and public-source notes in this folder. Evidence labels below mean **API contract** (platform owner's documentation), **implementation** (pinned source), **product or user report** (vendor documentation or a public issue), and **inference**. Product behavior does not establish its private API choices.

## The decisive boundary

“Locked” covers different execution environments: an already logged-in user's locked session, an OS login screen with no user session, and (on FileVault Macs) a boot-volume unlock before normal macOS services. The host must both survive the transition and run capture/input in the graphical session or below its compositor. A daemon's persistence alone does not put its GUI APIs in that session. Apple's launchd context explanation, Microsoft's Session 0 rule, and XDG portal's user-consent lifecycle make this a lifecycle and permission problem before it is an image-encoding problem. [Apple DTS](https://developer.apple.com/forums/thread/696859), [Microsoft interactive services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [XDG RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html).

## Windows: documented secure-desktop capture, session-local worker

**API contract.** `IDXGIOutput1::DuplicateOutput` explicitly returns `E_ACCESSDENIED` when the caller lacks rights to the current desktop image; Microsoft gives the secure desktop as an example accessible only to `LOCAL_SYSTEM`. It can return `DXGI_ERROR_UNSUPPORTED` during desktop or mode switches, and `IDXGIOutputDuplication::AcquireNextFrame` can return `DXGI_ERROR_ACCESS_LOST` when a desktop switch invalidates the duplication object. The latter requires releasing and recreating it. `DXGI_ERROR_WAIT_TIMEOUT` is merely no new frame. [DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput), [AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe).

**API contract.** Services run in Session 0 and do not directly interact with a user's session. `CreateProcessAsUserW` can launch a worker under a token in the intended session. `WTSGetActiveConsoleSessionId` returns the *physical console* session ID and can return `0xFFFFFFFF` during attach/detach; it does not choose an arbitrary RDP session. `WTSQuerySessionInformation` or session enumeration is needed if AUV deliberately supports RDP sessions. `OpenInputDesktop` returns the desktop currently receiving input within the caller's window station; `SetThreadDesktop` binds a thread to it, but fails if that thread already has windows or hooks on its current desktop. A dedicated desktop-bound thread or worker is consequently more robust than switching an existing UI thread. [Interactive services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw), [WTSGetActiveConsoleSessionId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid), [WTSQuerySessionInformationW](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsquerysessioninformationw), [OpenInputDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openinputdesktop), [SetThreadDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddesktop).

**Implementation.** Sunshine's service duplicates its LocalSystem token, sets `TokenSessionId` to the active console session, launches Sunshine with `CreateProcessAsUserW`, and checks session changes. Its display path opens the input desktop, binds the thread, and calls `DuplicateOutput1` or `DuplicateOutput`, with explicit `DXGI_ERROR_ACCESS_LOST` handling. These are source-backed mechanics, not proof of every GPU/RDP configuration. [Sunshine service, pinned `4429acd`](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/tools/sunshinesvc.cpp#L96-L161), [session supervision](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/tools/sunshinesvc.cpp#L247-L293), [desktop binding](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/src/platform/windows/misc.cpp#L213-L242), [DXGI capture](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/src/platform/windows/display_base.cpp#L72-L205).

**Implementation.** RustDesk also switches to `OpenInputDesktop`/`SetThreadDesktop` and separately calls Windows `SendSAS` for Ctrl+Alt+Del. Ordinary `SendInput` is subject to UIPI and reports only insertion of events, not login success; synthetic Ctrl+Alt+Del is not a substitute for the SAS API/policy. `SendSAS` has its own service/policy constraints. [RustDesk desktop code, pinned `b5d8b97`](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/platform/windows.cc#L273-L341), [RustDesk SAS](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/platform/windows.rs#L945-L1004), [Microsoft SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [Microsoft SAS policy](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-winlogon#softwaresasgeneration).

**Product claim.** Parsec says its *per-computer* Windows install starts under SYSTEM and permits login-screen access; a per-user install starts only after login. Its exact capture and input APIs remain unknown. [Parsec installation modes](https://support.parsec.app/hc/en-us/articles/32381368159124-Install-Parsec-App-on-Windows).

**AUV inference.** A Windows proof should install a LocalSystem lifecycle owner, place a worker in the chosen session, bind a fresh thread to the active input desktop, use DXGI duplication for full-display capture, and deliver ordinary keys/pointer input separately from SAS. Capture errors need to distinguish access denied, unsupported display mode/GPU, lost duplication, no frame, and session detach. Do not assume `WTSGetActiveConsoleSessionId` covers RDP. Keep UAC's secure desktop and pre-login Winlogon as separate test cases.

## macOS: GUI context is documented; third-party capture/input at LoginWindow is not

**API contract.** Apple DTS says a global LaunchAgent with `LimitLoadToSessionType=LoginWindow` runs in the login-window context as root; an Aqua agent runs in the user GUI context. A LaunchDaemon stays in the global context and cannot gain WindowServer access just by being root. This establishes where a probe must run, not that ScreenCaptureKit or event posting will succeed there. [Apple DTS on launchd contexts](https://developer.apple.com/forums/thread/696859), [TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html).

**API contract.** ScreenCaptureKit requests screen-recording permission and exposes `SCShareableContent` plus streams/screenshots. `CGPreflightScreenCaptureAccess` checks ordinary capture authorization without prompting. Apple offers the restricted `com.apple.developer.persistent-content-capture` entitlement for VNC apps needing persistent capture and requires an application to Apple. Neither page promises LoginWindow capture or silent permission at cold boot. PPPC's Screen Recording entry does not supply a general silent allow path. [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit), [Apple DTS on preflight](https://developer.apple.com/forums/thread/839069), [persistent entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.persistent-content-capture), [PPPC payload](https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web).

**API contract and uncertainty.** Core Graphics defines `kCGHIDEventTap` where HID events enter WindowServer and `kCGSessionEventTap` where HID/remote-control events enter a login session. `CGEventPost` and the post-event authorization preflight/request APIs are candidates for testing, but their documentation does not guarantee delivery to a locked login window. Capture, event-posting consent, successful event submission, password-field consumption, and authenticated session transition are five distinct observations. [Apple tap location](https://developer.apple.com/documentation/coregraphics/cgeventtaplocation/cgsessioneventtap), [Core Graphics functions](https://developer.apple.com/documentation/coregraphics/core-graphics-functions).

**Implementation.** RustDesk's current macOS source distinguishes `/dev/console` UID 0 during LoginWindow, installs `/Library/LaunchAgents`, and has explicit `login/<asid>` versus `gui/<uid>` handling. It is valuable implementation evidence for the lifecycle but does not by itself prove that AUV's ScreenCaptureKit/xcap and input paths work there. [RustDesk macOS, pinned `b5d8b97`](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/platform/macos.rs#L640-L745), [LoginWindow launch handling](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/platform/macos.rs#L1200-L1290).

**Product claim.** Parsec documents a separate macOS installer for access after reboot, wired Ethernet, FileVault disabled, and a `/Library/LaunchAgents/com.parsec.app.plist`. This supports feasibility for a configured *OS login screen*, while leaving Parsec's private capture/input mechanisms unknown. It is not evidence for the FileVault preboot unlock UI. [Parsec macOS login-screen guide](https://support.parsec.app/hc/en-us/articles/32381618319124-Access-Login-Screen-on-macOS), [Apple FileVault deployment](https://support.apple.com/guide/deployment/intro-to-filevault-dep82064ec40/web).

**Public report and implementation boundary.** A [Codex issue](https://github.com/openai/codex/issues/32913) reports one failed locked-use request; it is not a general capability contract. The open-source [trycua/cua VNC client](https://github.com/trycua/cua/blob/02fdd98ad59a00752bdccea396164cdefbe2afb5/libs/lume/src/VNC/VNCClient.swift) controls a VM virtual console through RFB, a different boundary from the host login screen. Neither source proves that ordinary host in-session capture and input can operate a cold login screen. See the [public-source comparison](2026-09-27-sky-cua-lock-screen-research.md).

**Important API distinction.** Apple documents Authorization Services plug-ins and `AuthorizationRightSet` for policy extension, but warns that `AuthorizationTagsPriv.h` is not public API and that authorization plug-ins are brittle across OS updates. Apple DTS has called one change to the `system.login.screensaver` configuration unsupported; a different DTS discussion recommended a specific configuration for a specific macOS 14 plug-in issue. These sources do not endorse replacing the system unlock mechanism as an AUV product path. [Apple plug-in guide](https://developer.apple.com/documentation/security/extending-authorization-services-with-plug-ins), [DTS on unsupported configuration and brittleness](https://developer.apple.com/forums/thread/824458), [DTS on macOS 14 plug-in compatibility](https://developer.apple.com/forums/thread/737268).

**AUV inference.** First test an already logged-in locked session using the existing signed build. Next, if an owner approves cold LoginWindow access, build a minimal signed `LoginWindow` agent plus Aqua agent and persistent service to test screen pixels, TCC identity, CGEvent receipt, logout/login handoff, and fast user switching. Do not commit to ScreenCaptureKit or an authorization plug-in as the product path until those gates pass. Treat FileVault preboot as a separate boundary; Apple silicon/macOS 26 SSH FileVault unlock is a separate remote-unlock feature, not screenshot/input. [Apple SSH unlock](https://support.apple.com/guide/deployment/intro-to-filevault-dep82064ec40/web).

## Linux: portal session versus DRM scanout and virtual devices

**API contract.** The XDG RemoteDesktop portal creates a user-mediated session, starts it with a selection dialog, and yields PipeWire streams and authorized input devices. A restore token can fail and prompt again. This path is not a guaranteed unattended greeter channel. Linux `uinput` creates a virtual keyboard/pointer after opening `/dev/uinput`, setting event bits, and issuing `UI_DEV_SETUP`/`UI_DEV_CREATE`. The active greeter compositor and seat must accept that device. [XDG portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), [XDG session lifetime](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Session.html), [kernel uinput guide](https://docs.kernel.org/input/uinput.html).

**Implementation.** Sunshine's KMS backend uses `drmModeGetFB2` and `drmPrimeHandleToFD` and temporarily enables `CAP_SYS_ADMIN`. Its ordinary documented Linux service is user-scoped, so KMS capability does not establish a pre-login host lifecycle. [Sunshine KMS, pinned `4429acd`](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/src/platform/linux/kmsgrab.cpp#L42-L177), [framebuffer export](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/src/platform/linux/kmsgrab.cpp#L625-L845), [Sunshine setup](https://github.com/LizardByte/Sunshine/blob/4429acd026f7942115c58aeaa7d0ea50a33d0ca9/docs/getting_started.md).

**Current RustDesk implementation, correcting the early proposal.** The merged opt-in DRM path has the existing root `--service` capture/export active scanout DMA-BUFs to an unprivileged `--server`; rendering/detiling is done by that consumer. The service starts a greeter `--server` as the active seat0 user and the input path creates `/dev/uinput` keyboard/mouse devices. An early design discussion described a separate capability-bearing `drmtap-helper`, but that is **not** the final merged architecture. [RustDesk DRM consumer, pinned `b5d8b97`](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/server/drm_capturer.rs#L1-L25), [root producer and greeter launch](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/platform/linux.rs#L1073-L1150), [uinput path](https://github.com/rustdesk/rustdesk/blob/b5d8b979d8723921902eef9d33c83ff0580fed7b/src/server/input_service.rs#L749-L770), [early proposal](https://github.com/rustdesk/rustdesk/discussions/15417).

**Observed limit.** RustDesk issue #15791 documents an actual SDDM Plasma Wayland greeter test at 2880×1800: frame, ASCII password typing, and absolute click worked after fixes to login-screen detection, layout, and input routing. It expressly leaves GDM and non-ASCII greeter text unproved. This is upstream's reported integration result, not our reproduction. The issue also shows that a working DRM frame path can coexist with an empty display list or input silently routed to X11. [RustDesk greeter issue and validation](https://github.com/rustdesk/rustdesk/issues/15791).

**AUV inference.** A Linux greeter path needs a boot service, active seat/compositor identification, authorized DRM read or compositor-specific capture, an accepted virtual input device, physical/logical layout calibration, and keyboard layout handling. Validate SDDM/Plasma, GDM/GNOME, X11 greeters, multiple GPUs, monitor sleep, and non-ASCII input as separate claims. Do not make an ordinary Portal/PipeWire success count as pre-login support.

## AUV's current boundary and credential-recording consequence

**Current implementation.** AUV's macOS window capture uses ScreenCaptureKit with an xcap fallback, while display/region capture uses xcap; Windows display capture uses xcap. Windows global input calls `SendInput`; these paths have no proven secure-desktop/session worker. The first-party local Runner is spawned as a daemon child and serves through an inherited channel; unless session placement changes, it inherits the daemon's environment rather than magically joining LoginWindow/Winlogon/the active greeter. [macOS capture](../../../../crates/auv-driver-macos/src/session.rs), [Windows capture](../../../../crates/auv-driver-windows/src/capture.rs), [Windows input](../../../../crates/auv-driver-windows/src/input.rs), [Runner registration](../../../../crates/auv-cli/src/commands/serve.rs), [Runner spawn](../../../../crates/auv-daemon/src/daemon/runner.rs), [local Runner](../../../../crates/auv-cli/src/runner/local_driver.rs).

**Credential boundary.** `input.typeText` and `input.keyboard` currently accept literal text; `encode_args` copies string arguments into an `InvokeRequest.inputs` map, and CLI arguments include the text. The local CLI tracing event reviewed here emits only frontend lifecycle, and the input-result artifact contains `InputActionResult` delivery metadata rather than the typed text; the reviewed `CreateRunRequest` has devices/labels, not command inputs. Thus we have **not** established that this specific path currently writes a password to `records.jsonl`, but we *have* established that it enters CLI argv and in-memory invoke/protocol values, and future replay/transport/logging could expose it. Do not reuse generic `input.typeText` or `input.keyboard` for credentials without an explicit secret-aware contract and a review of every frontend, transport, replay, trace, report, screenshot, and error path. [typed input args](../../../../crates/auv-cli-invoke/src/commands/input.rs), [argument encoding](../../../../crates/auv-cli-invoke/src/command.rs), [invoke root](../../../../crates/auv-cli/src/commands/invoke.rs), [result artifact](../../../../crates/auv-driver-common/src/input.rs), [run protocol](../../../../proto/auv/api/daemon/v1/run.proto).

For a feasibility probe, use a disposable test account and a harmless key/click first. Store diagnostic frames only when they cannot include a secret; record session state and API/error codes separately from content. The existing `InputActionResult.verified` field already distinguishes delivery from semantic success. A login success claim requires an independently observed session transition, not a successful `CGEventPost`, `SendInput`, `uinput` write, or capture call. [AUV `InputActionResult`](../../../../crates/auv-driver-common/src/input.rs).

## Decision-ready gates

1. **Windows first if cross-platform delivery is the goal:** official LocalSystem/DXGI contract and two pinned implementations make this the clearest route. Test Winlogon capture/input, locked user, UAC secure desktop, console detach, and DXGI reinitialization individually.
2. **macOS first for a macOS target:** probe a locked existing session before packaging a LoginWindow agent. A successful lock probe does not answer cold login, and a successful LoginWindow agent launch does not answer TCC/capture/input.
3. **Linux by explicit distro/display-manager target:** an SDDM Wayland success from RustDesk is a useful precedent, not a portable Linux guarantee.

Any implementation is a new platform-specific driver/lifecycle feature requiring an owner-approved slice. Reuse AUV's capture result, `InputActionResult`, tracing, and separate verification seam; introduce session metadata and failure layers only after the probe identifies what they must express. Do not build a generic login-screen abstraction from these source reviews alone.
